## What settles software acceptance

The existing solve-loop service now carries the original Requirement, task,
source observations, test results, rejected envelopes and independent
receiving as native source Cells. Schema.org and PROV-O identifiers describe
source code, activities, attribution, use and derivation. The native source
record and witnesses determine standing; a vocabulary identifier alone does
not authenticate a provider or establish acceptance.

Each receiving condition is the original triple
`(candidate, met-when.cell, requirementSource)`. The exact original condition
text and additional authored fields remain in the Requirement body. Only
direct measured Cells from the host-selected receiving envelope supply
positive acceptance evidence. Opposition from all admitted sources at that
same coordinate remains relevant. Structural projection of a receipt body
does not grant its embedded claims receiving authority.

The resulting control policy is explicit:

- Passing local tests with absent or incomplete receiving yields `verified`.
- Complete, direct, unopposed receiving yields `accepted`.
- Denial restores the observed baseline before another bounded proposal.
- Contradiction restores the baseline and returns `contested` for the owner.
- A lost observation, unreported source change or false restoration stops
  later producers with `needs-recovery`.

The callback host owns effects and authenticates the selected receiver.
Producer and receiver names inside the library are attribution and contract
checks. They are not an authentication mechanism. The full test and receipt
bodies survive control decisions as source observations; a Boolean test
result cannot become a receiving witness.

A real local source-edit fixture gives the first candidate a passing local
test but an independent negative-input counterexample. The loop restores
the actual file, retains the denial, proposes corrected code, and receives
that second revision. The complete 33-case source run also checks stale
candidate and Requirement cuts, partial admission, source changes during
tests or receiving, callback errors, non-data results and mutating resolver
selection. Its pre-issuance diagnostic uses the actual received Craft
candidate and native issued suppliers; final installed-cohort receipts are
recorded separately when available.

## Pulse, circulation and requirements production

MAPE-K can be assessed through the actual source path: monitor supplies
measured Cells; analysis settles the original knowledge; planning consumes
the admitted Requirement and source-bound design; execution uses original
transactions; knowledge retains the original evidence. An invocation or
clock pulse does not itself witness learning, delivery or acceptance.
Likewise, PACE-S, circuit, board and organizational decisions require their
own admitted source and effect contracts. This work does not claim an entire
enterprise loop merely from a scheduler or a state name.

The original host integration is responsible for retaining a useful
verified proposal while independent receiving is unavailable, reusing that
proposal on an unchanged waiting pulse, and invalidating it when its
Requirement, design, source or selected receiving provider changes. The
original journal must retain byte and exact-number witnesses through its
native codec and recheck the full cut before resuming an effect. These
consumer changes require their own source and installed-cohort receipts.

The upstream market/sensor-to-normative composition remains described in
[the original Requirement source finding](market-requirement-source-lineage.md).
The already-qualified original Specification PR preserves condition identity
and explicit interpretations, and is integrated. It still produces a draft
requiring independent admission. The legacy drafting/record routes and
current host composition contain specific unresolved source-custody seams;
this solver consumes an admitted Requirement and does not silently replace
those owners with a second derivation engine.
